1. How to Use This Guide

This document gives you command of why the frontend was built the way it was — not just what each component renders. Section 4 is a chronological build procedure you can recite. Sections 5–9 are deep dives into each significant file with the reasoning behind specific implementation choices. Section 10 lists rejected alternatives. Section 11 rehearses the questions a panel is most likely to ask about the frontend, each with a tight model answer.

The one idea to hold onto

The frontend has no build-time router, no global state library, and no chart library — and that is a deliberate scope decision, not an oversight. The app has exactly one structural route split (customer app vs. admin panel), state that only ever needs to live in the component that uses it, and a handful of simple bar/histogram visualisations. Every dependency actually used (React, Vite, Tailwind, DOMPurify) earns its place; nothing was added "because it's standard."

2. The Frontend at a Glance

The frontend is a single React application built with Vite, split into two independent shells that share no state: the customer-facing app and the admin dashboard. Both are plain function components — there is no Redux/Context state management because no piece of state is needed by more than one component subtree.

3. Design Philosophy — Why React + Vite, and Why No Router

Three frontend stacks were actually compared during Phase 1 design (see the project's own tool comparison from the presentation deck), and the same reasoning still holds for the final build:

FactorVite + React (chosen)AngularPlain HTML/CSS/JS
SpeedVery fast dev server (native ES modules, no bundling in dev)Slower due to large framework sizeFast to load, but inefficient to build/maintain at scale
ScalabilityHighly scalable — component-based, easy to add tabs/panelsCapable but overly complex for this project's scopePoor — becomes unmanageable as features grow
CostFreeFreeFree
Usability for the teamEasy to learn, flexible, rapid developmentSteep learning curve (strict structure, DI, RxJS)Inefficient for a multi-view app with shared state (chat + forms + dashboard)

Within React, the decision to not add react-router-dom was made because the app only has one meaningful route split: customer app vs. admin panel. That split is resolved once, at the earliest possible point, by reading window.location.pathname directly in main.jsx: 

const isAdmin = window.location.pathname.startsWith('/admin')

ReactDOM.createRoot(document.getElementById('root')).render(
  <React.StrictMode>
    {isAdmin ? <AdminPanel /> : <App />}
  </React.StrictMode>
)

Everything else — switching between "Chat Support", "Outage Status" and "Report a Fault", or between the four admin tabs — is not real navigation at all. It's a single useState variable (tab) controlling which child component renders, inside one already-mounted page. A router library exists to manage browser history, deep-linkable URLs, and nested route trees — none of which this app needs, since none of its internal tabs need their own shareable URL or back-button behaviour.

Why this matters for a viva

If asked "why no React Router?", the honest and correct answer is the app doesn't have enough distinct routes to justify one — adding a routing library to manage two states (isAdminRoute ? <AdminPanel/> : <App/>) would be exactly the kind of unnecessary abstraction good engineering avoids. If the project grew to need shareable/bookmarkable URLs for individual chat sessions or fault report references, that would be the point at which a router becomes justified.

4. Step-by-Step: How the Frontend Was Designed and Built

This is the procedure to recite when asked "walk me through how you built the interface."

1

Scaffold the app shell around the four customer needs, not around pages

Before any component was styled, the four customer needs identified in the requirements (chat, outage status, fault reporting, escalation) were mapped directly to three visible tabs plus one always-visible action (the 0800-POWER call button in the header) — the navigation structure is a direct reflection of the problem statement, not an afterthought.

2

Set up Vite with Tailwind, and configure the dev-server proxy immediately

Vite was chosen for near-instant dev server startup and hot reload. Tailwind was configured up front so every component from the first commit onward used utility classes directly in JSX — no separate CSS files to keep in sync per component. The proxy rules (/api → backend REST, /ws → backend WebSocket) were set up in vite.config.js before writing any component, so every component could assume relative URLs work regardless of what host the page was loaded from.

3

Build the chat UI against the WebSocket contract first

ChatWindow.jsx was built first because it is the most complex piece of client state: an open socket, a running message list, and a typing indicator. Getting the connect/reconnect/send/receive lifecycle right early meant every later feature (ratings, feedback, escalation banners) could be added as an incremental extension of an already-working message loop instead of being designed alongside connection-handling bugs.

4

Add the outage board and fault-report form as independent, self-contained widgets

Both OutageBoard.jsx and FaultForm.jsx were deliberately built to own their own state and fetch their own data (no props from a parent, no shared context) — each is a tab that can be developed, tested, and reasoned about in complete isolation from the chat logic.

5

Wire up feedback loops (ratings, thumbs up/down) once the chat was stable

The 1–5 star session rating and per-message helpful/unhelpful buttons were added after the core chat worked, because they depend on the backend already returning a message_id per bot reply — a dependency that only existed once the database write-path (Section 8 of the backend guide) was finished.

6

Build the admin panel as a second, independent React root — not a protected route inside the main app

Rather than nesting an admin view inside the customer App component behind a permission check, the admin panel was built as an entirely separate component tree (AdminPanel.jsx) selected at the earliest possible point (main.jsx). This keeps admin-only code (fault report queue, escalations, analytics, RAG audit) completely out of the bundle path a regular customer's browser reasons about, and avoids any chance of an admin-only UI element flashing on screen before an auth check completes.

7

Move admin auth from a hardcoded frontend password to a backend-issued token

The earliest version checked the password in frontend code. Once backend token auth was added, LoginGate was rewritten to POST the password once to /admin/login, store only the returned opaque token in sessionStorage, and every subsequent admin call was routed through a single adminFetch() wrapper that automatically attaches Authorization: Bearer <token>. This is the frontend half of the security hardening described in the backend guide.

8

Build the analytics dashboard by hand instead of importing a charting library

Only three visualisation shapes were actually needed: a KPI stat card, a horizontal bar (intent distribution), and a vertical histogram (1–5 star ratings). All three were implemented as small components using plain Tailwind width/height percentages driven by inline style — avoiding a charting library dependency for a handful of simple bars.

9

Harden the rendering of AI-generated content against XSS

Once bot replies were being rendered with dangerouslySetInnerHTML (needed to show **bold** emphasis and multi-line formatting), every bot message was passed through DOMPurify.sanitize() with an explicit allow-list of safe tags (strong, em, br, ul, li, p) before being rendered — closing the XSS risk inherent in rendering raw model output as HTML.

10

Make the app reachable from any device on the network

vite.config.js was set to host: true (bind to 0.0.0.0 instead of just localhost), and config.js's WS_URL was written to derive the WebSocket host from window.location.host at runtime rather than a hardcoded localhost:8000. Together, these two changes are what let a phone or another laptop on the same Wi-Fi load the app by IP address and have chat still connect correctly, with zero configuration change.

5. Deep Dive 1 — Real-Time Chat UI (ChatWindow.jsx)

Session identity is a client-generated random ID, not a login

function genSessionId() {
  return 'sess-' + Math.random().toString(36).slice(2, 10)
}

Because Kanea is anonymous customer support (no account system), a session needs an identity only for the duration of one browser tab's conversation — enough to group messages, ratings, and feedback together in the database. The ID is generated once via useState(genSessionId) (the initializer form, so it only runs on first render) and reused for the life of the component.

WebSocket lifecycle: connect, reconnect with backoff, clean up

ws.onclose = () => {
  setConnected(false)
  // Backoff: 1s → 2s → 4s → 8s … capped at 30s
  const delay = Math.min(1000 * Math.pow(2, retryCount.current), 30_000)
  retryCount.current += 1
  retryTimeout.current = setTimeout(connect, delay)
}

Exponential backoff exists so a dropped connection doesn't hammer the backend with reconnect attempts every second — each failure waits longer than the last, up to a 30-second ceiling, and retryCount resets to zero the moment a connection succeeds (in onopen). The useEffect cleanup function clears any pending retry timeout and closes the socket on unmount, preventing a reconnect loop from continuing after the component is gone.

Rendering AI output safely

function sanitize(text) {
  const html = formatISODates(text).replace(/\*\*(.*?)\*\*/g, '<strong>$1</strong>')
  return DOMPurify.sanitize(html, { ALLOWED_TAGS: ['strong', 'em', 'br', 'ul', 'li', 'p'] })
}

Two transforms happen before sanitisation: raw ISO timestamps embedded in bot replies (e.g. from live outage data) are converted to human-readable local date/time strings via formatISODates(), and Markdown-style **bold** emphasis from the LLM's output is converted to <strong> tags. Only then is the result run through DOMPurify with an explicit allow-list — this ordering matters: sanitisation must be the last step, so nothing added by the earlier transforms can reintroduce unsafe markup.

Why the rating prompt appears after exactly 5 bot replies

addMessage() increments a botMsgCount counter on every bot message and flips showRating to true the instant the count reaches 5. This is a deliberate UX threshold: too early (e.g. after 1 message) and the user hasn't had enough interaction to judge quality; too late (e.g. only at disconnect) and many users would never see the prompt at all because they simply close the tab.

Per-message feedback is tied to the backend's message ID

Thumbs up/down buttons only render if (isBot && msg.message_id && !feedback) — the ID comes from the backend's database write (db.save_message() returns the row's auto-increment ID), so feedback can be attributed to one specific stored message rather than "the last bot reply," which would be ambiguous if messages arrived out of order or the array re-rendered.

6. Deep Dive 2 — Outage Board (OutageBoard.jsx)

Polling instead of a live connection

useEffect(() => {
  load()
  const id = setInterval(load, 60_000)   // refresh every minute
  return () => clearInterval(id)
}, [])

The outage board deliberately uses simple 60-second polling of GET /outages rather than a WebSocket. Outage status changes on the scale of minutes-to-hours (the backend's own scraper only refreshes hourly — see the backend guide, Section 7), so a persistent connection would add complexity for no meaningful gain in freshness. Polling is the right-sized tool here, in contrast to chat, where a WebSocket is justified by genuinely sub-second interaction.

Client-side filtering keeps the UI instantly responsive

The area search box and status filter buttons (all / active / scheduled / resolved) both filter the already-fetched outages array in-memory (Array.filter), rather than re-querying the backend per keystroke. Given the dataset size (a handful to a few dozen outage records), this avoids unnecessary network round-trips and gives filtering that feels instantaneous.

Defensive date formatting

fmt(iso) wraps new Date(iso) in a try/catch and falls back to showing the raw string if parsing fails, and separately treats a missing estimated_restoration as "TBD" rather than showing "Invalid Date" — because the scraper (backend) can legitimately return null for restoration time when ECG's website hasn't published one yet.

7. Deep Dive 3 — Fault Report Wizard (FaultForm.jsx)

Why a 3-step wizard instead of one long form

Splitting into Customer Details → Fault Type & Urgency → Review & Submit reduces the perceived effort of the form (one short screen at a time) and lets each step validate independently before the user can proceed — critical for a stressed customer reporting a possibly dangerous fault, who shouldn't have to scroll through a long form under pressure.

Per-step validation gating

const canNext = [
  () => form.customer_name && form.phone && form.location,
  () => form.fault_type && form.urgency,
  () => true,
]

Each step has its own validator function in an array indexed by the current step; the "Next" button is disabled until canNext[step]() returns true. This keeps validation logic co-located with the step definitions rather than one large conditional, and makes it trivial to add or reorder steps.

The danger notice is derived from data already collected, not asked for twice

Both the review screen and the post-submission success screen check ['critical', 'high'].includes(form.urgency) to show a "call 0800-POWER now" banner — the urgency value the customer already selected in Step 2 is reused to decide whether to escalate the visual warning, rather than adding a redundant "is this an emergency?" question.

Failure handling matches the safety stakes of the form

If POST /fault-report fails, the error message explicitly directs the customer to call 0800-POWER rather than just saying "try again" — because a failed fault report for a dangerous situation (fallen wire, sparking transformer) must never leave the customer with only a silent retry as their only guidance.

8. Deep Dive 4 — Admin Panel & Analytics Dashboard

Token storage: sessionStorage, not localStorage

sessionStorage.setItem(TOKEN_KEY, token)

The admin token is stored in sessionStorage deliberately: it is cleared automatically when the browser tab is closed, unlike localStorage which would persist indefinitely on a shared or public machine. This narrows the window during which a stolen or forgotten session could be reused.

One authenticated-fetch wrapper, used everywhere

export function adminFetch(url, options = {}) {
  const token = sessionStorage.getItem(TOKEN_KEY) || ''
  return fetch(url, {
    ...options,
    headers: { ...(options.headers || {}), Authorization: `Bearer ${token}` },
  })
}

Every admin tab (FaultReportsTab, EscalationsTab, RagSourcesTab) calls adminFetch() instead of the raw fetch() — this guarantees the Bearer token is attached consistently and means a future change to the auth header (e.g. a refresh-token scheme) only needs to be made in one place.

Each tab owns its own loading/error/data state

FaultReportsTab, EscalationsTab, and RagSourcesTab are structured identically: local loading/error/data state, a load() function called on mount, and a manual "Retry"/"Refresh" button. This repetition is intentional at this scale — three tabs with near-identical but not fully identical rendering (fault reports have urgency colour coding, escalations have a status badge, RAG sources have nested source lists) don't yet justify extracting a shared generic-list abstraction.

Analytics — hand-built visualisations instead of a charting library

SatisfactionHistogram and IntentBar are both implemented as plain <div> elements whose height/width is set via inline style as a percentage of the maximum value in the dataset: 

const pct = max > 0 ? Math.round((count / max) * 100) : 0
...
<div className={`h-full ${meta.color} rounded-full`} style={{ width: `${pct}%` }} />

This avoids adding a charting dependency (e.g. Chart.js, Recharts) for what is, in total, one bar chart and one histogram — both of which are simpler to hand-build with Tailwind than to configure through a general-purpose charting API.

9. Deep Dive 5 — App Shell, Routing & Network Configuration

Two independent entry points selected by URL path

Both main.jsx and App.jsx independently check window.location.pathname.startsWith('/admin'). This is deliberately checked at the entry point (main.jsx) so the admin bundle path never renders any customer UI at all, and the same check exists defensively inside App.jsx in case it is ever rendered directly.

The proxy is what makes relative URLs possible

// vite.config.js
server: {
  host: true,          // listen on 0.0.0.0 — reachable from other devices on the LAN
  proxy: {
    '/ws':  { target: 'ws://localhost:8000', ws: true, changeOrigin: true },
    '/api': { target: 'http://localhost:8000', rewrite: p => p.replace(/^\/api/, ''), changeOrigin: true }
  }
}
// config.js
export const API = '/api'
export const WS_URL = (id) => `ws://${window.location.host}/ws/${id}`

Because every request goes through /api or /ws and is proxied server-side by Vite to localhost:8000, the frontend code never needs to know the backend's real address. WS_URL builds its target from window.location.host — whatever hostname or IP address the browser actually used to load the page — so opening the app at http://192.168.1.20:5173 from a phone on the same Wi-Fi automatically connects its WebSocket to ws://192.168.1.20:5173/ws/..., which Vite then proxies through to the backend. No environment variable or config change is needed to demo the app on another device.

10. Design Trade-offs — Alternatives Considered

Client-side routingreact-router-domOnly one real route split exists (customer vs. admin); a single path check at the entry point achieves the same result with zero dependency and zero route-config boilerplate.
Global state managementRedux / Context API / ZustandNo piece of state is needed outside the component that owns it — each tab/component fetches and owns its own data. Adding a global store would centralise state nothing actually shares.

Styling approachComponent-level CSS files / CSS-in-JS (styled-components)Tailwind's utility classes keep styling co-located with markup, avoid a separate stylesheet per component to keep in sync, and were the fastest fit for a small team building many small UI states (loading/error/empty/success) per component.

11. Anticipated Defense Questions & Model Answers

Why React and Vite specifically, and not Angular or plain JS?
The project's own Phase-1 comparison (speed, scalability, cost, usability) favoured Vite+React: near-instant dev server reloads, a component model that scales cleanly as tabs/panels were added, free and open-source, and a gentler learning curve than Angular's stricter framework structure. Plain HTML/CSS/JS was rejected because a multi-view app with shared UI patterns (loading/error states, forms, live data) becomes unmanageable without componentisation.
Why is there no router library if there are multiple "pages"?
The three customer tabs and four admin tabs aren't real navigable routes — none of them need a shareable URL, deep-linking, or back-button semantics; they're just "which component is currently shown," which a single useState handles. The only structural route split (customer vs. admin) is resolved once at the entry point by reading window.location.pathname directly.
How does the frontend stay secure when rendering AI-generated text as HTML?
Bot messages are rendered via dangerouslySetInnerHTML to support bold text and line breaks, but every message is first passed through DOMPurify.sanitize() with an explicit allow-list of six safe tags. Sanitisation runs last, after markdown-to-HTML and date formatting transforms, so nothing those earlier steps introduce can bypass the filter.
What happens if the WebSocket connection drops mid-chat?
The onclose handler schedules a reconnect with exponential backoff (1s, 2s, 4s, 8s, capped at 30s), shows a "Reconnecting…" indicator, and resets the backoff counter the moment a new connection succeeds — so a brief network blip recovers quickly, while a longer outage doesn't spam the server with reconnect attempts.
How does the same frontend build work both on localhost and from another device on the network?
The WebSocket URL is built at runtime from window.location.host rather than a hardcoded address, and the Vite dev server is configured with host: true to bind to 0.0.0.0. Whatever hostname/IP a browser used to load the page is automatically reused to reach the backend through the same Vite proxy, so no environment-specific configuration is needed to demo on a phone or another laptop on the same Wi-Fi.
Why is the admin panel a completely separate component tree instead of a protected route inside the main app?
Selecting between App and AdminPanel happens at the earliest possible point, in main.jsx, before any customer-facing component ever mounts. This means admin-only UI and data never even exists in memory for a regular customer's session, and there's no risk of an admin element flashing on screen before an auth check resolves.
How is the admin password protected on the frontend?
The password itself is never stored in frontend code or state beyond the login form input; it's sent once to POST /admin/login, which returns an opaque token. That token is stored in sessionStorage (cleared when the tab closes) and attached automatically to every subsequent admin request through a single adminFetch() wrapper.
Why does the outage board poll every 60 seconds instead of using a live connection?
The backend's own scraper only refreshes live outage data once an hour, so a WebSocket here would add complexity without any real gain in freshness. 60-second polling is a right-sized match for how often the underlying data can actually change, in contrast to chat, where sub-second delivery is genuinely needed.
Why is filtering on the outage board done client-side instead of via API query parameters?
The dataset is small (a handful to a few dozen records fetched once per minute), so filtering the already-loaded array in memory gives instant, no-network-latency results as the user types or clicks a status filter — adding server-side query parameters would only add round-trip latency for no benefit at this scale.
Why build the analytics charts by hand instead of using a charting library like Chart.js?
Only two visual shapes are needed — a horizontal bar (intent distribution) and a vertical histogram (star ratings) — both trivially expressed as Tailwind-styled divs with an inline percentage width/height. A charting library would add a dependency and API surface disproportionate to two simple bar visualisations.
How does per-message feedback (thumbs up/down) know which exact message it's rating?
Every bot reply the backend sends includes the database row ID it was saved under (message_id). The feedback buttons only render once that ID is present and post it back verbatim to /message-feedback, so a rating is always attributed to one specific stored message rather than inferred from message order.
Why a 3-step wizard for the fault report form instead of one page?
Splitting details, fault type/urgency, and review into separate steps reduces perceived effort and allows per-step validation to gate progress — important for a customer who may be reporting a dangerous situation under stress and shouldn't have to navigate one long, all-at-once form.
If this were to scale to many more users, what in the frontend would need to change first?
Each admin tab currently fetches its own data independently with no caching or pagination — at high data volumes, /admin/fault-reports and similar endpoints would need pagination and the tabs would need to request pages rather than full lists. The chat and outage board components themselves are already per-session/stateless on the client and would not need structural changes.

12. Glossary of Key Terms

TermMeaning in this project
SPA (Single-Page Application)The entire customer app or admin panel runs as one HTML page; tab switches are in-memory state changes, not full page reloads
Vite dev-server proxyConfiguration that forwards /api and /ws requests from the frontend's port to the backend's port, so the browser only ever talks to one origin
Exponential backoffA reconnect strategy where each retry waits longer than the last (1s, 2s, 4s, 8s…), preventing repeated-failure spam
DOMPurifyA JavaScript library that strips unsafe HTML/script content from a string before it's rendered, used here to sanitise AI-generated chat replies
Session token (Bearer auth)A random string issued by the backend after a successful admin login, sent in the Authorization header on every subsequent admin request instead of the password
sessionStorage vs localStorageBoth are browser key-value stores; sessionStorage clears when the tab closes, localStorage persists indefinitely — the admin token intentionally uses the former
Optimistic/self-owned component stateEach tab component manages its own loading/error/data state independently rather than relying on a shared global store
Utility-first CSS (Tailwind)A CSS approach where small, single-purpose classes (e.g. px-4, rounded-xl) are composed directly in markup instead of writing custom CSS rules per component
