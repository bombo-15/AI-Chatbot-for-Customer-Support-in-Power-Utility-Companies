1. Executive Summary

This chatbot's LLM backend changed twice in one week. On 23 Aug 2026, Groq (a Llama-family model) was replaced with OpenRouter's free-tier openai/gpt-oss-20b:free, mainly to escape Groq's tight rate caps. On 26 Aug 2026, that was replaced again with Claude Haiku 4.5 via the official Anthropic SDK, mainly for better instruction-following and factual precision. Re-running the same 20-case evaluation after each change gives a clear, if not entirely flattering, picture:

✓ Reliability improved at every step

Fallback rate ("I'm having a technical issue"): Groq 15% (3/20) → OpenRouter 5% (1/20) → Claude 0% (0/20) in its final, shipped configuration. Claude also fixed OpenRouter's one regression (q-19) and recovered a fact OpenRouter had given up on (q-1).

✗ Text-overlap quality never recovered to the Groq baseline

BERTScore F1: 0.898 (Groq) → 0.861 (OpenRouter) → 0.862 (Claude). ROUGE-1 F1: 0.474 → 0.451 → 0.425. Claude essentially matches OpenRouter on these metrics — slightly better on ROUGE-2 and BERTScore, slightly worse on ROUGE-1 — but both sit clearly below Groq.

ⓘ A prediction that didn't pan out: Claude got more verbose, not less

Going into Stage 2, the expectation (based on Claude's reputation for stronger instruction-following) was that switching to Claude would fix OpenRouter's verbosity problem. It didn't — it made it worse. Average response length: Groq 36 words → OpenRouter 74 words → Claude 122 words, against a 56-word reference average. Claude answers are clean, accurate, and well-structured (markdown headers, tables, bullet lists) — but that structure is exactly what keeps diluting n-gram-overlap scores like ROUGE. This is the single most actionable finding in this report: the system prompt's existing "under 120 words" instruction is being followed loosely at best, and needs tightening regardless of provider.

ⓘ A reliability scare that turned out to be this sandbox, not Claude

The first two live Claude eval runs hit unexplained fallbacks (15% and 20%). Because the original error handler swallowed exceptions silently, the cause wasn't visible — so logging was added, which revealed APITimeoutError (a dropped connection, not a rate limit or model error) on a different, unrelated query each time. That pointed to network flakiness in this local dev sandbox rather than a Claude reliability problem. Bumping the SDK's retry budget from 1 to 2 attempts resolved it: the next run was a clean 0/20 fallbacks, and that fix is now shipped in chatbot.py.

2. Background — Two Migrations

Stage 1 — 23 Aug 2026, commit 5c21d7e

"Migrate LLM provider from Groq to OpenRouter, improve retry/escalation logic": switched the LLM call to OpenRouter's free-tier openai/gpt-oss-20b:free model (1,000 requests/day vs. Groq's tighter tokens-per-minute caps), added retry-with-backoff for transient failures, and fixed a bug where technical/rate-limit failures were silently triggering [ESCALATE_TO_AGENT].

Stage 2 — 26 Aug 2026, this session

Replaced the raw OpenRouter HTTP call with the official anthropic Python SDK, model claude-haiku-4-5, motivated by two OpenRouter-era findings from Stage 1: verbose, markdown-heavy answers, and a subtle unit-labelling error (GHp vs. GH₵ on a tariff figure). Also required setting up billing on Anthropic's Console, since — unlike Groq and OpenRouter's free-tier models — the Claude API has no standing free tier.

3. Methodology

Identical across all three runs: the same 20 hand-written gold Q&A pairs in backend/eval/test_response_quality.json, each run live through chatbot.get_bot_response() (no mocking), scored with rouge-score (ROUGE-1, ROUGE-2) and bert-score (model roberta-large). Only the LLM provider changed between runs — same test cases, same scoring code, same knowledge base. Reproduce any stage with:

6.1 The reliability diagnostic (methodology note)

The first live Claude run scored 17/20 (3 fallbacks: q-8, q-10, q-16). Because chatbot.py's error handler caught and discarded the exception with no logging, the cause was invisible. A one-line log statement was added (print(f"[chatbot] Claude API call failed ({type(e).__name__}): {e}")), and the eval was re-run: 16/20 this time (4 different fallbacks: q-9, q-12, q-18, q-20), all logged as anthropic.APITimeoutError — a dropped connection, not a rate limit, not an auth or content issue. Different, unrelated queries failing each run is the signature of network flakiness rather than a systematic problem, and is plausibly specific to this local sandboxed dev environment rather than Claude's API. Raising MAX_RETRIES from 1 to 2 in chatbot.py and re-running produced a clean 20/20, which is the run reported everywhere else in this document. The lesson generalises past this one bug: a silently swallowed exception is not a fixed exception, just an invisible one.

8. Discussion & Recommendations

Was the second migration worth it?

Yes, on balance, but not for the reason expected going in. Claude did not fix the verbosity problem found in Stage 1 — it made it measurably worse (74 → 122 words). What it did deliver: perfect reliability once properly configured (0/20 vs. OpenRouter's 1/20 and Groq's 3/20), a fixed regression, a recovered fact, and no recurrence of the unit-mislabelling bug across all 20 cases. The raw ROUGE/BERTScore numbers are a wash against OpenRouter and still below the original Groq baseline.

  1. Tighten the system prompt for conciseness — now the top priority. The existing instruction ("under 120 words unless detail is essential") is not landing. Given Claude's strong instruction-following reputation didn't fix this on its own, the next step is testing an explicit, stronger constraint (e.g. a hard sentence-count cap, "no headers, no closing questions, no bold unless quoting a figure") and re-measuring with this same harness — don't assume a prompt change will work; verify it the same way this report verified the provider change.
  2. Keep MAX_RETRIES = 2. This is now load-bearing, not cosmetic — it was the difference between 0/20 and 15-20/20 fallbacks in this environment. Re-verify it under production network conditions (e.g. on Render) rather than assuming this sandbox's flakiness generalises.
  3. Never let an exception handler swallow silently again. The one-line fix in §6.1 turned an unexplained, unreproducible failure into a two-minute root cause. Apply the same pattern anywhere else in the codebase that catches a broad exception type without logging it.
  4. Re-run this harness after any future provider or prompt change. Three runs in one document is what made the verbosity trend and the reliability regression visible in the first place — a single before/after snapshot would have missed both.

9. Conclusion

Across two migrations, Kanea's chatbot became strictly more reliable (85% → 95% → 100% real-answer rate on this 20-case sample) while its ROUGE/BERTScore quality metrics never returned to the original Groq baseline, settling instead on a plateau shared by both post-Groq providers. The dominant explanation held up under a second test: answer verbosity, not correctness, drives most of the metric gap, and it got worse, not better, with the switch to Claude. Two concrete engineering wins came out of the evaluation process itself rather than the model choice: a silent-failure logging gap that was hiding a real (if environment-specific) reliability issue, and confirmation that OpenRouter's unit-mislabelling bug does not recur under Claude. The system prompt, not the provider, is now the clearest lever left for closing the remaining quality gap.
