1. Executive Summary

This report scores the actual text the Kanea chatbot generates — not the routing decisions or retrieval hit-rate that EVALUATION.md already covers, but the sentences a customer would actually read. Twenty realistic ECG/PURC customer questions were sent through the real, live pipeline (real Groq LLM calls, no mocking) and the replies were compared against hand-written gold-reference answers grounded in the same knowledge base Kanea itself retrieves from, using three complementary automatic metrics: ROUGE-1, ROUGE-2, and BERTScore.

Three findings drive the rest of this report:

  • The BERTScore/ROUGE gap is the headline result. BERTScore F1 (0.898) is far higher than ROUGE-2 F1 (0.278) because Kanea's LLM paraphrases the knowledge base rather than copying it verbatim — exactly what a helpful assistant should do, and exactly what n-gram metrics are least equipped to reward. See §7.1.
  • 3 of 20 live calls (15%) hit a Groq API error and fell back to Kanea's built-in "I'm having a technical issue" message instead of a real answer — a reliability finding, not a language-quality one. See §7.2.
  • 7 of 20 static, FAQ-style questions (35%) were mis-routed to the "dynamic" (live outage) path by the keyword intent classifier, reproducing — with real evaluation queries — the exact keyword-tie weakness EVALUATION.md §7.2 already flagged as deferred future work. This measurably cost quality: mis-routed cases scored ~3 BERTScore points and ~11 ROUGE-1 points lower on average. See §7.3.

2. Why This Evaluation Exists

Kanea's existing evaluation framework (EVALUATION.md, backend/eval/evaluate.py) deliberately scores five separate pipeline layers — intent classification, query routing, the safety-critical danger trigger, RAG retrieval, and live operational metrics — because a single pipeline-wide "accuracy" number can't describe a system built from that many independent decision points. That framework explicitly named one layer it could not score automatically:

From EVALUATION.md §6 — "Response-quality (qualitative, not automated here)"

"The LLM's actual generated text (tone, faithfulness to the retrieved context, conciseness) isn't scored by evaluate.py — doing that automatically needs either an LLM-as-judge pass or a human rubric, and both cost real API calls / time that felt out of scope for an offline, free-to-re-run script."

This report fills that specific gap using the standard NLP toolkit for scoring generated text against a reference: ROUGE (lexical n-gram overlap, the standard for summarization/QA evaluation since 2004) and BERTScore (contextual-embedding similarity, 2019, designed specifically to catch paraphrases that ROUGE penalizes). It does not replace the human-rubric approach §6 also recommends for tone/faithfulness judgement — see §8 for where the two approaches differ and why both still have a place.

3. Methodology

3.1 Test set construction

20 customer questions were written to span every static, RAG-answerable section of Kanea's knowledge base — 14 sections from ecg_knowledge.txt and 6 from purc_knowledge.txt — deliberately mirroring the section coverage of the existing RAG retrieval test set (backend/eval/test_retrieval.json) so the two evaluations can be read side by side. For each question a gold-reference answer was hand-written, grounded strictly in the same source text Kanea's retriever can see — never containing a fact the knowledge base doesn't state.

Dynamic queries (live outage status) and escalation queries were intentionally excluded from this particular test set: their "correct" answer depends on mutable live-scraped data or on a fixed hand-off script, not on stable reference text, so ROUGE/BERTScore against a static gold answer would not be a meaningful comparison for them. Static, knowledge-grounded FAQ questions are where text-similarity-to-a-reference is actually the right evaluation tool.

3.2 What was actually run

Each of the 20 queries was sent through chatbot.get_bot_response() — the exact function main.py calls for a real user message — with a fresh session per case. This exercises the entire live pipeline: keyword intent classification → query-type routing → TF-IDF RAG retrieval over the ECG/PURC knowledge base → system-prompt construction → a real network call to the Groq API (llama-3.3-70b-versatile, temperature 0.4) → escalation-tag stripping. No component was mocked or stubbed; the candidate answers scored below are exactly what a real Kanea user would have received for that message.

3.3 Scoring

Each (reference, candidate) pair was scored with:

  • rouge-score v0.1.2 — Google's reference implementation, use_stemmer=True, for ROUGE-1 and ROUGE-2.
  • bert-score v0.3.13 — the reference implementation from Zhang et al. (2020), model roberta-large (the package's own English default), lang="en", no baseline rescaling.

Both are open-source, deterministic-given-the-same-text libraries; the only source of run-to-run variance is the Groq LLM's own sampling temperature, not the scoring itself.

4. Metric Definitions — ROUGE-1, ROUGE-2, BERTScore

4.1 ROUGE-1 and ROUGE-2 (lexical n-gram overlap)

ROUGE-N measures how many contiguous sequences of N words ("n-grams") the candidate text shares with the reference text. ROUGE-1 compares single words (unigrams); ROUGE-2 compares consecutive word pairs (bigrams), which makes it far stricter — it only rewards overlap when the candidate uses the reference's exact word order, not just its vocabulary. 

Precision = (matching n-grams) / (n-grams in candidate)
Recall    = (matching n-grams) / (n-grams in reference)
F1        = 2 · Precision · Recall / (Precision + Recall)

Precision asks "how much of what the bot said is grounded in the reference wording"; Recall asks "how much of the reference's content did the bot's answer cover." use_stemmer=True means "connection" and "connections" count as the same token, so the score isn't punished by routine morphology.

4.2 BERTScore (contextual semantic similarity)

BERTScore replaces exact string matching with meaning matching. Both the candidate and reference are passed through a pretrained transformer (here, roberta-large) to get a contextual embedding vector for every token — the same word gets a different vector depending on its sentence, which is what lets it recognize that "reconnect your meter" and "restore your electricity supply" are saying almost the same thing even though they share zero words. 

For each candidate token: find its highest-cosine-similarity match among reference tokens → avg = Precision
For each reference token: find its highest-cosine-similarity match among candidate tokens → avg = Recall
F1 = 2 · Precision · Recall / (Precision + Recall)

This greedy, order-independent matching is exactly why BERTScore tolerates paraphrasing and reordering that ROUGE-2 penalizes heavily — and exactly why it must be read alongside ROUGE, not instead of it: BERTScore can score two sentences as highly similar even when they diverge on a specific fact (a date, a phone number, a tariff figure), because a single wrong token barely moves an average over dozens of embedding dimensions. §7.1 and §7.4 show concrete cases of this trade-off in Kanea's own results.

4.3 Why all three, together

MetricRewardsBlind to
ROUGE-1Using the reference's vocabularyWord order; synonyms; paraphrase
ROUGE-2Using the reference's exact phrasingAny valid rewording — heavily penalizes a fluent paraphrase
BERTScorePreserving meaning, in any wordingSpecific facts/numbers being swapped or dropped

No single one of these three numbers can answer "is Kanea's response good?" on its own — that is precisely why EVALUATION.md's framework already scores the pipeline in layers rather than with one number, and why this report keeps that same principle for the generation layer.

How to read a BERTScore F1 around 0.90–0.91

BERTScore F1 is not scaled 0–1 the way accuracy is — even two unrelated English sentences typically score 0.80–0.85 on roberta-large, because most of the score reflects shared function words, grammar, and topic-level embedding similarity rather than content overlap. A score in the 0.90s indicates strong content alignment for this model; it should be read relative to the per-case range in §6 (0.797–0.992 here), not against an absolute 0–1 scale.

7. Discussion & Findings

7.1 The BERTScore/ROUGE-2 gap is the paraphrasing signature, not a quality problem

Averaged across all 20 cases, ROUGE-2 F1 is 0.278 while BERTScore F1 is 0.898 — a 62-point gap on a comparable 0–1 scale. Reading the actual transcripts (Appendix, §10) shows why: Kanea's LLM almost never copies the reference's exact phrasing. For q-9 ("How do I report a fault to ECG?"), the reference reads "you can report a fault by contacting your ECG District Office, calling 0302 611 611..."; the candidate reads "To report a fault, you can contact your District Office, call 0302 611 611..." — the same facts, reordered and reworded, which ROUGE-2 scores relatively well here (0.638) precisely because the phrase structure happens to survive. Cases like q-1 and q-13 show the more typical pattern: correct content, restructured sentence, ROUGE-2 near zero, BERTScore still 0.84–0.90. This is exactly the failure mode BERTScore's design paper identifies ROUGE-N as vulnerable to, and it is the concrete justification — visible in Kanea's own output, not just in the abstract — for reporting BERTScore alongside ROUGE rather than ROUGE alone.

The reverse caution matters equally: BERTScore does not verify facts. q-1 ("What is ECG and when was it established?") scores a respectable 0.843 BERTScore F1 even though the candidate answer declines to give a founding date at all (see §7.4) — the response is topically on-target and fluently written, which is most of what BERTScore measures, but it doesn't answer the question asked. A high BERTScore is evidence of fluent, on-topic, semantically-aligned text; it is not, by itself, evidence of factual completeness.

7.2 Reliability: 3 of 20 live calls (15%) hit an internal error fallback

q-16, q-18, and q-20 all returned the identical string: "I'm having a technical issue right now. Please call 0800-POWER (0800-76937) for immediate assistance." — the hard-coded fallback inside chatbot.py's try/except around the Groq HTTP call (backend/chatbot.py, get_bot_response). Because that exception is caught and replaced with fallback text rather than propagated, the specific cause (timeout, rate limit, or transient network error) isn't visible from outside the function — this evaluation ran 20 requests in quick succession with only a 0.5s gap between them, which is a plausible trigger. These three cases pull every aggregate metric down substantially (their BERTScore F1 sits at 0.797–0.835, noticeably below the 0.898 all-case mean) purely because the fallback sentence is semantically unrelated to the reference answer — not because the LLM generated a poor answer to the question. This is why §5 reports both the all-20 and the 17-excluding-failures numbers side by side: the 17-case figures (ROUGE-1 F1 0.545, BERTScore F1 0.914) are the fairer read of generation quality; the all-20 figures are the fairer read of what a real user actually experiences, reliability included.

7.3 Intent-routing errors measurably reduce answer quality

7 of the 20 static, FAQ-style questions (35%) were classified as query_type = "dynamic" by chatbot.classify_intent() / classify_query_type() — the path meant for live outage questions, not billing or safety FAQs. This is not a new bug: EVALUATION.md §1 already documented that the intent classifier is pure keyword substring matching with no tie-breaking logic, and §7.2 named "replace the keyword classifier" as deferred future work. What this evaluation adds is a measured, real-query cost of leaving that gap open:

GroupnAvg RAG docs retrievedAvg ROUGE-1 F1Avg BERTScore F1
Correctly routed to static103.00.5890.926
Mis-routed to dynamic72.00.4810.896

(Excludes the 3 API-failure cases from §7.2 so routing effects aren't confounded with them.) The mechanism is visible in the code: _build_rag_context() (backend/chatbot.py) fetches top_n=5 documents for a static query but only top_n=2 for a dynamic one, on the assumption that dynamic queries need RAG only as light "supplemental background." A mis-routed FAQ question therefore gets less than half the knowledge-base context it should, which shows up here as a real, if modest, drop in both metrics — larger in ROUGE-1 (−11 points) than in BERTScore (−3 points), consistent with BERTScore's greater tolerance for a shorter-but-still-on-topic answer. The specific trigger is the same one EVALUATION.md already diagnosed: several keywords appear in more than one intent's keyword list (e.g. "electricity" and "voltage" under outage_status, "connection" and "apply" under billing), classify_intent() breaks ties with Python's max() over a dict, and outage_status is declared first in INTENT_KEYWORDS — so every tie defaults to outage_status. All 7 mis-routed cases here are consistent with that exact tie pattern.

7.4 RAG retrieval misses cause honest — but unhelpful — refusals

q-1 ("What is ECG and when was it established?") retrieved purc_overview and ecg_prepaid_meters instead of the correct ecg_company_overview section, and the LLM correctly declined to invent a founding date it wasn't given — matching the system prompt's explicit instruction not to speculate. q-14 ("current electricity tariff for a residential customer using 200 units a month") retrieved purc_non_residential_electricity_tariffs and purc_special_load_tariffs instead of the correct purc_residential_electricity_tariffs section, and the candidate answer states "I'm not provided with the current residential tariff information" rather than quoting a non-residential rate as if it applied to a residential customer. In both cases this is the safer of two failure modes — Kanea did not hallucinate a specific fact, which is the behavior EVALUATION.md's response rules are designed to enforce — but it is still a usefulness failure traceable to the TF-IDF retriever: q-1's query uses "established" where the source text says "commenced," and q-14's "200 units a month" doesn't share literal tokens with "0-300 kWh," so neither query's bag-of-words overlaps enough with the correct section to clear MIN_RELEVANCE_SCORE ahead of a competing section. This is the same literal-token-overlap limitation EVALUATION.md §4 already measured (Precision@5 = 0.463) and §7.2 named as the reason a move to semantic/embedding-based retrieval was deferred rather than attempted — this report's q-1 and q-14 are concrete real-question instances of exactly that gap.

7.5 Best and weakest cases

Best: q-2 — "Which districts are part of the Tema region?" (ROUGE-1 F1 0.971, BERTScore F1 0.992)

A closed-list factual question with one unambiguous correct source document. The candidate reproduced the district list almost verbatim, which is exactly the kind of question where high lexical overlap is both achievable and a legitimate quality signal — the "right" answer has very little room for valid paraphrase.

Weakest (excluding API failures): q-14 — tariff lookup with a RAG miss (ROUGE-1 F1 0.130, BERTScore F1 0.817)

Covered in §7.4 above — a retrieval failure, not a generation failure. The lowest scores in this dataset trace back to retrieval or infrastructure, not to the LLM writing a poor sentence once it has the right facts in front of it.

8. Limitations of This Evaluation

  • n = 20 is a small sample. Individual case scores are illustrative; the averages are indicative, not statistically definitive. The set was sized to give complete, hand-verifiable coverage of every static knowledge-base section rather than to support tight confidence intervals.
  • One reference answer per query. ROUGE and BERTScore both compare against a single gold answer; a differently-phrased but equally correct response can legitimately score lower. Multi-reference scoring (several acceptable gold answers per query) would tighten this but multiplies the hand-authoring effort.
  • Non-deterministic generation. Groq calls used temperature 0.4, so re-running this exact script will not reproduce identical scores — the API-failure count and exact per-case numbers are a snapshot of one run, though the qualitative findings (§7.1–§7.4) reflect structural properties of the pipeline, not one-off luck.
  • BERTScore's model is general-purpose, not domain-tuned. roberta-large was pretrained on general English text, not ECG/utility terminology specifically; it has no special notion of a correct tariff figure or phone number — see §7.1's caution about facts.
  • Scope is static/RAG-answerable queries only. Dynamic (live outage) and escalation-path responses are not covered by this metric pair, for the reason given in §3.1 — a live-data or fixed-script answer isn't well served by comparison to a static gold reference.
  • This complements, not replaces, the human-scored faithfulness/tone/relevance rubric EVALUATION.md §6 recommends. ROUGE and BERTScore can tell you a response is lexically or semantically close to a reference; they cannot tell you it is empathetic, correctly toned for a utility customer, or appropriately concise — that still needs a human rater.
